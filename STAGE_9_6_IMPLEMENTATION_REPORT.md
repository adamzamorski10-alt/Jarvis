## 4. SECURITY BOUNDARIES

ExecutionBridge enforces:

1. **No execution handles leaked to model** — Bridge returns `ExecutionPrepareResult`/`ExecutionResult` containing plan_id and execution metadata, never executor instances.
2. **No forbidden imports** — ExecutionBridge has zero imports of subprocess, shell, filesystem APIs, Git, ToolExecutionService, PermissionEngine, VerificationGate, RunController, WorkspaceManager, DevelopmentAgent.
3. **No arbitrary execution** — `execute()` only calls `AutonomousPlanExecutor.execute_plan(plan_id)`.
4. **No model-controlled execution fields** — plan_id is deterministic from intent_id; project_id is application parameter; task/run/execution IDs are generated by TaskRepository.
5. **Approval scope binding** — Approval `scope_fingerprint` is recomputed at execution time and compared against stored approval. Replay across different intent/capability/project/risk is rejected.
6. **One-time consumption** — `CapabilityApprovalService.consume()` uses atomic SQL UPDATE with rowcount check. Concurrent consumers: exactly one wins.
7. **Execution-time recheck** — `execute()` always re-evaluates `PolicyCapabilityGate` fresh. Policy changes between prepare and execute are caught.
8. **Fail-closed** — DENIED, DISABLED, REJECTED, missing approval, expired approval, consumed approval, planning failure, execution failure all raise exceptions. No silent success.

## 5. APPROVAL SEMANTICS

### State Machine

```
PENDING → APPROVED (application approval action)
PENDING → DENIED (application denial action)
PENDING → CANCELLED (application cancellation action)
PENDING → EXPIRED (lazy expiration on access)
APPROVED → CONSUMED (atomic consumption at execution time)
```

### Scope Fingerprint

Computed from:
- `intent_id`
- `capabilities` (sorted)
- `effective_risk`
- `operation_type`
- `project_id`

Trusted application code only. Model cannot provide the final fingerprint.

### Consumption

- Atomic SQL UPDATE: `UPDATE approvals SET status='CONSUMED' WHERE approval_id=? AND status='APPROVED'`
- If `rowcount == 0`: return None (concurrent consumption or invalid state)
- Lazy expiration: `get_pending()` checks `is_expired()` and marks EXPIRED before returning

## 6. REPLAY PROTECTION

| Attack Vector | Protection | Result |
|--------------|-----------|--------|
| Execute twice with same ManagerResult | Frozen model + deterministic plan_id + task state machine | Safe — same plan, idempotent task execution |
| Execute twice with same approval | Atomic consume + scope verification | Second call raises `ExecutionAuthorizationError` |
| Execute after success | Approval consumed; second call fails on consume | Blocked |
| Execute after cancellation | Task state machine prevents restart of cancelled tasks | Blocked at task level |
| Execute after failure | Task state machine enforces attempt limits | Blocked at task level |
| Execute after approval expiration | Lazy expiration check in `_verify_approval_scope` | Blocked |
| Execute after approval consumption | Status check in `_verify_approval_scope` | Blocked |
| Approval for project A used for project B | Scope fingerprint mismatch | Blocked |
| Approval for intent A used for intent B | Scope fingerprint mismatch | Blocked |
| Approval for capability A used for capability B | Scope fingerprint mismatch | Blocked |
| Approval for LOW risk used for MEDIUM risk | Scope fingerprint mismatch | Blocked |

## 7. CONCURRENCY BEHAVIOR

### Concurrent execute() with same approval

1. Call 1: `_verify_approval_scope()` loads approval (APPROVED), verifies scope, calls `consume()`
2. Call 2: `_verify_approval_scope()` loads approval (still APPROVED in DB until Call 1 commits), verifies scope, calls `consume()`
3. SQLite serializes the two UPDATE statements. One succeeds (rowcount=1), one fails (rowcount=0).
4. Loser raises `CapabilityApprovalStateError` → wrapped as `ExecutionAuthorizationError`.

**Invariant: ONE approval → at most ONE successful consumption.**

### Concurrent execute() with different approvals

- Both approvals are consumed independently.
- Both calls plan the same decision (deterministic plan_id).
- Both call `AutonomousPlanExecutor.execute_plan(plan_id)`.
- TaskStateMachine uses atomic SQL UPDATE to claim tasks. Only one worker can claim each task.
- **Safe** — task-level concurrency is handled by existing state machine.

### Concurrent policy changes

- `execute()` always calls `PolicyCapabilityGate.authorize()` fresh.
- If policy changes between calls, the new policy is authoritative.
- **Safe** — execution-time recheck wins.

## 8. CANCELLATION / FAILURE / RECOVERY

ExecutionBridge delegates to `AutonomousPlanExecutor.execute_plan()` which:

1. Accepts `cancel_event: asyncio.Event | None`
2. Checks `cancel_event.is_set()` before each scheduling iteration
3. Returns `PlanExecutionState.CANCELLED` when cancelled
4. Handles `TaskNotStartableError`, `StaleStateTransitionError`, `DependencyUnmetError`, `MaxAttemptsExceededError` by continuing loop or returning terminal state
5. On unexpected exception, checks task status from repository and returns FAILED if terminal

**ExecutionBridge does NOT introduce a second lifecycle authority.**

## 12. KNOWN LIMITATIONS

1. **Scope verification reads approval twice** — `_verify_approval_scope()` calls `get_approval()` then `consume()`. In high-concurrency scenarios, there is a theoretical TOCTOU window between these calls. However, `consume()` is atomic (single SQL UPDATE with rowcount check), so the worst case is a concurrent modification between the two calls, which `consume()` handles safely.

2. **Approval creation in prepare()** — Each `prepare()` call creates a new approval request. Repeated `prepare()` calls for the same decision will create multiple approvals. Application code should cache the `ExecutionPrepareResult` to avoid approval flooding.

3. **No persistent execution authorization cache** — `prepare()` must be called before `execute()`. If the application loses the `ExecutionPrepareResult`, it must re-prepare. This is intentional for security (no long-lived authorization tokens).

4. **Limited execution target** — Stage 9.6 only supports the existing autonomous development-plan execution path. Generic capability execution is NOT implemented.
