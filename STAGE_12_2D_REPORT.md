# Stage 12.2D — Durable Scheduler Execution Handoff

## Final Status

**STAGE_12_2D_PASS**

## 1. Scope Confirmation

Implemented ONLY the durable handoff boundary:
- Scheduler claimed occurrence → authorized existing execution path → durable scheduler TRIGGERED state / execution identifier
- `SchedulerHandoffService` with `handoff_task()` and `handoff_plan()` methods
- Target validation (task/plan existence and startability)
- Claim ownership verification before handoff
- Durable TRIGGERED state recording with execution identifier
- Failure-safe handoff (no false completion, no authorization bypass)

NOT implemented:
- Scheduler worker/polling loop
- Cron/interval calculation
- New claim/lease mechanism
- New task execution engine
- New plan execution engine
- REST endpoints
- Scheduler events/history integration
- Distributed locking
- External side effects
- New authorization system
- Changes to existing task state semantics

## 2. Exact Execution Entry Points Used

### Task Execution
**Entry point:** `AutonomousRunController.start_run(task_id)`

This is the narrowest existing application-owned entry point for task execution. It:
1. Fetches the task from `TaskRepository`
2. Checks startability (not COMMITTED/CANCELLED, not already RUNNING/VERIFYING/PASSED)
3. Delegates to `AutonomousTaskOrchestrator.start_task()`
4. Orchestrator calls `TaskStateMachine.claim_attempt()` which atomically transitions PENDING → RUNNING with attempt_count+1
5. Runs the full lifecycle with verification, repair loop, and timeout handling
6. Returns `AutonomousRunResult`

The scheduler does NOT bypass any of these checks. Authorization, approval, and verification remain entirely within the execution layer.

### Plan Execution
**Entry point:** `BackgroundExecutionManager.start_execution(plan_id, executor_factory)`

This is the narrowest existing application-owned entry point for plan execution. It:
1. Checks app is not shutting down
2. Checks plan is not already executing (in-memory)
3. Creates `InternalExecutionHandle` with unique `execution_id`
4. Launches `AutonomousPlanExecutor.execute_plan()` as background asyncio task
5. Returns `ExecutionHandleInfo`

The scheduler does NOT bypass any of these checks.

## 3. Authorization Flow

The scheduler handoff service performs ZERO authorization checks. It delegates entirely to the existing execution layer:

- **Task execution:** `AutonomousRunController.start_run()` → `AutonomousTaskOrchestrator.start_task()` → `TaskStateMachine.claim_attempt()` → `TaskRepository.claim_task_attempt()`
  - TaskStateMachine enforces state transition matrix
  - TaskRepository enforces attempt_count < max_attempts
  - Orchestrator enforces verification, approval, and commit requirements

- **Plan execution:** `BackgroundExecutionManager.start_execution()` → `AutonomousPlanExecutor.execute_plan()` → `PlanExecutionService` → `AutonomousRunController.start_run()` per task
  - Same task-level authorization applies

Scheduler claim/lease proves scheduler ownership of the occurrence ONLY. It is NOT authorization to execute.

## 4. Target Validation

Before handoff, the service validates:

**For tasks:**
1. Task exists in `TaskRepository`
2. Task status is not terminal (not COMMITTED, not CANCELLED)
3. Task status is not already active (not RUNNING, VERIFYING, PASSED)

**For plans:**
1. `BackgroundExecutionManager.start_execution()` validates the plan is not already executing
2. `PlanNotExecutableError` is raised if app is shutting down

If target validation fails, handoff returns `HandoffResult(success=False)` and the scheduler occurrence remains CLAIMED for retry.

## 5. Claim Ownership

Only the current valid scheduler claimant may perform handoff. The service verifies:

1. `occurrence_id` exists in scheduler DB
2. `claim_token` matches exactly
3. `status == CLAIMED`
4. `lease_until > now` (lease is still valid)

All verification happens in a single read-then-delegate pattern. The handoff to the execution layer is a separate step. If execution fails, the scheduler occurrence remains CLAIMED (or can be marked FAILED by 12.2E).

## 6. Execution ID Semantics

### Task Execution
**Durable execution identifier:** `task.execution_token`

Generated by `TaskRepository.claim_task_attempt()`:
```python
exec_token = f"exec_{uuid.uuid4().hex[:12]}"
```

This token is:
- Generated atomically with the PENDING → RUNNING state transition
- Persisted in the `development_tasks` table
- Survives process restarts
- Unique across concurrent claims

The scheduler stores this token in `scheduled_jobs.execution_id` after successful handoff.

### Plan Execution
**Non-durable execution identifier:** `BackgroundExecutionManager.execution_id`

Generated by `BackgroundExecutionManager.start_execution()`:
```python
execution_id = f"exec_{uuid.uuid4().hex[:12]}"
```

This token is:
- Generated when the background task is queued
- Stored ONLY in memory (`_handles_by_exec_id` dict)
- LOST on process restart
- NOT durably persisted

**Documented limitation:** If the process crashes after plan execution starts but before the scheduler records TRIGGERED, the `execution_id` may be lost. Recovery must use plan-level durable markers (task execution_tokens, events) to reconcile.

## 7. TRIGGERED Definition

`TRIGGERED` means **exactly**:

> The scheduler has successfully handed the occurrence to the existing execution layer and recorded a durable execution reference in `scheduled_jobs.execution_id`.

TRIGGERED does NOT mean:
- Task completed
- Plan completed
- Verification passed
- External side effect succeeded
- Commit succeeded

TRIGGERED is the scheduler's durable marker that "I have delegated this occurrence to the execution layer." The execution layer owns all subsequent state transitions.

## 8. Crash-Window Analysis

### A. Crash before execution request
- **Scheduler state:** CLAIMED (with valid lease)
- **Task/plan state:** Unchanged
- **Recovery:** Scheduler worker polls again, lease may have expired, recovery resets to PENDING
- **Duplicate execution:** None

### B. Crash while submitting execution
- **Scheduler state:** CLAIMED (transaction not committed yet, or committed but execution not started)
- **Task/plan state:** Unchanged
- **Recovery:** On restart, scheduler sees CLAIMED with expired lease → recovery resets to PENDING → re-claim and handoff
- **Duplicate execution:** None

### C. Execution request accepted but process crashes before scheduler persistence
- **Scheduler state:** CLAIMED (execution started but TRIGGERED not recorded)
- **Task state:** RUNNING (with execution_token)
- **Plan state:** Background task running (in-memory execution_id)
- **Recovery:** 
  - For tasks: RecoveryManager detects RUNNING task with stale heartbeat → handles via existing recovery
  - For plans: Process restart loses in-memory execution_id, but tasks within plan have execution_tokens
- **Duplicate execution:** Possible for plans if worker re-handoffs after restart. For tasks, TaskStateMachine prevents duplicate claim.

### D. Scheduler persistence succeeds but execution process crashes
- **Scheduler state:** TRIGGERED (with execution_id)
- **Task state:** RUNNING (with execution_token)
- **Plan state:** Background task crashed
- **Recovery:** 
  - For tasks: RecoveryManager handles RUNNING task
  - For plans: BackgroundExecutionManager cleans up handle; tasks may need individual recovery
- **Duplicate execution:** None

### E. Execution starts but scheduler remains unaware
- **Scheduler state:** CLAIMED
- **Task state:** RUNNING
- **Recovery:** Same as case C
- **Duplicate execution:** Possible if scheduler re-handoffs

### F. Scheduler restarts with TRIGGERED occurrence
- **Scheduler state:** TRIGGERED (durable)
- **Task state:** RUNNING/VERIFYING/PASSED/COMMITTED/FAILED
- **Recovery:** Scheduler knows execution was delegated. 12.2E will advance to next occurrence based on terminal task state.
- **Duplicate execution:** None

### G. Stale claimant attempts handoff after lease expiry
- **Scheduler state:** CLAIMED (but lease expired)
- **Recovery:** Another worker recovers via `reset_expired_claim_to_pending`
- **Stale claimant handoff:** FAILS — lease check blocks
- **Duplicate execution:** None

## 9. Idempotency Analysis

### Existing Execution Layer Idempotency

**Task execution:** The existing `TaskRepository.claim_task_attempt()` provides AT_MOST_ONCE task execution claim via atomic CAS:
```sql
UPDATE development_tasks
SET status = 'RUNNING',
    attempt_count = attempt_count + 1,
    started_at = :now,
    execution_token = :token
WHERE task_id = :task_id
  AND status = :expected_status
  AND attempt_count < :max_attempts
```

Only one concurrent worker can successfully claim a task. Subsequent claims fail the WHERE clause.

**Plan execution:** `BackgroundExecutionManager` provides in-memory duplicate prevention via `_plan_to_exec_id` mapping. However, this is NOT durable across restarts. Two separate processes could both start the same plan if they don't share memory.

### Scheduler Handoff Idempotency

The scheduler handoff is idempotent within a single process lifetime:
- Duplicate handoff attempt for same occurrence: FAILS (status is already TRIGGERED)
- Stale claimant handoff: FAILS (claim_token mismatch or lease expired)

Across process restarts:
- If scheduler recorded TRIGGERED: handoff is not retried
- If scheduler did NOT record TRIGGERED (crash window C): handoff may be retried, but task-level CAS prevents duplicate execution

## 10. Failure Semantics

### Handoff fails before execution request
- Scheduler occurrence remains CLAIMED
- No task/plan state mutation
- Safe for retry (lease may need renewal)

### Handoff fails after execution request (task rejected)
- Scheduler occurrence remains CLAIMED
- Task state may have changed (e.g., task became terminal between validation and execution)
- Safe for retry

### Execution layer raises exception
- Scheduler occurrence remains CLAIMED
- No task state mutation (exception occurred before `claim_task_attempt` succeeded)
- Safe for retry

### Handoff succeeds but process crashes before TRIGGERED persistence
- Task state: RUNNING (with execution_token)
- Scheduler state: CLAIMED
- Recovery: Existing task recovery handles RUNNING task. Scheduler recovery resets expired claim.
- Possible duplicate handoff after restart, but task CAS prevents duplicate execution.

## 11. Concurrency Analysis

### Two scheduler claimants
- Handled by Stage 12.2C atomic claim. Only one claimant can successfully claim.

### Stale claimant vs current claimant
- Handoff service verifies `claim_token` and `lease_until > now`
- Stale claimant fails on both checks

### Handoff vs lease expiry
- Handoff service checks `lease_until > now` before delegating to execution
- If lease expires during handoff execution, the execution layer may still succeed
- Scheduler occurrence remains CLAIMED; 12.2E handles advancement

### Handoff vs recovery
- Recovery requires `status = 'CLAIMED' AND lease_until <= now`
- Handoff requires `status = 'CLAIMED' AND lease_until > now`
- These are mutually exclusive

### Duplicate handoff attempt
- Second handoff attempt fails because `finalize_triggered` requires `status = 'CLAIMED'`
- After first handoff, status is TRIGGERED

### Restart during handoff
- If scheduler crashes before TRIGGERED: occurrence remains CLAIMED
- If scheduler crashes after TRIGGERED: occurrence is TRIGGERED (durable)
- Recovery handles both cases

## 12. Security Findings

- **No scheduler bypass of permissions:** Scheduler handoff delegates to existing execution layer which enforces all authorization
- **Claim tokens remain internal:** Not exposed through handoff service output
- **No secret leakage:** Handoff service processes no credentials
- **Target identifiers validated:** Task/plan existence checked before execution
- **No arbitrary execution:** Schedule expressions parsed by calculator only, never executed
- **Scheduler persistence ≠ authorization:** Claim ownership does not grant execution permission
- **No new privileged path:** Handoff service is a thin wrapper around existing entry points

## 15. Defects Found and Fixed During Implementation

No concrete defects found in the existing execution architecture that block Stage 12.2D. The handoff service is a thin, safe wrapper.

**Design limitation documented:** `BackgroundExecutionManager.execution_id` is in-memory only and NOT durably persisted. This is a pre-existing architectural constraint, not a defect introduced by this stage.

## 16. Defects Found and Fixed During Hostile Gate

1. **Task execution_token not always captured:** Original code only captured `execution_token` for `SUCCEEDED`/`RUNNING`/`VERIFYING` run results. Failed tasks with `execution_token` would record empty `execution_id` in TRIGGERED. **Fix:** Always capture `execution_token` when task exists, regardless of run result status.

## 16. Known Limitations

1. **Plan execution_id is non-durable:** `BackgroundExecutionManager.execution_id` is stored only in memory. On process crash after plan execution starts but before scheduler records TRIGGERED, the execution_id is lost. Recovery must use task-level durable markers.

2. **Task handoff is synchronous:** `AutonomousRunController.start_run()` is called synchronously and blocks until the task completes or times out. The lease must be long enough to cover the handoff + initial execution start. For long-running tasks, the lease may expire before execution completes. This is by design — the execution layer manages its own lifecycle.

3. **Plan handoff is fire-and-forget:** `BackgroundExecutionManager.start_execution()` queues the plan execution and returns immediately. The scheduler records TRIGGERED before the plan actually starts executing. If the plan fails to start (e.g., executor_factory raises), the scheduler may have already recorded TRIGGERED. This is acceptable because TRIGGERED only means "delegated to execution layer."

4. **No scheduler-side retry policy:** Failed handoffs leave the occurrence as CLAIMED. 12.2E must implement retry/backoff logic.

5. **No event/history integration:** Handoff events are not emitted. 12.2E or later stages may add this.

## 17. Exact Guarantees and Non-Guarantees

| Layer | Guarantee | Not a guarantee |
|-------|-----------|-----------------|
| Scheduler claim ownership | Atomic DB transition; exactly one valid owner durably | Exactly-once delivery (AT_LEAST_ONCE) |
| Lease ownership | Valid while `lease_until > now`; expired at `lease_until` | Indefinite ownership without renewal |
| Handoff boundary | Delegates to existing execution layer; records TRIGGERED on success | Task/plan completion |
| Task execution claim | AT_MOST_ONCE via `TaskRepository.claim_task_attempt()` atomic CAS | Exactly-once execution |
| Plan execution | AT_LEAST_ONCE (in-memory duplicate prevention only) | Exactly-once execution |
| External side effects | UNKNOWN | Idempotency |

**Exact guarantees:**
- Scheduler handoff does not bypass any existing authorization, approval, or verification checks
- Scheduler claim/lease is not treated as execution authorization
- Only current valid claimant can perform handoff
- TRIGGERED means successful delegation to execution layer, not execution completion
- Failed handoffs leave scheduler state unchanged for safe retry
- Task execution claim is AT_MOST_ONCE via existing atomic CAS
- No new privileged execution path is introduced

**Non-guarantees:**
- Exactly-once scheduler delivery (AT_LEAST_ONCE by design)
- Exactly-once task execution (AT_MOST_ONCE claim, but execution may fail and be retried)
- Exactly-once plan execution (in-memory duplicate prevention only)
- Idempotent external side effects
- Durable plan execution_id across restarts

## 19. Final Hostile Gate

### 19.1 CLAIMED → TRIGGERED Proof

**Actual code path** (`handoff.py` → `repository.py`):

```python
# handoff.py validates:
job = await self._scheduler_repo.get_job_by_occurrence_id(occurrence_id)
assert job.claim_token == claim_token
assert job.status == SchedulerJobStatus.CLAIMED
assert job.lease_until > now

# repository.py atomic UPDATE:
UPDATE scheduled_jobs
SET status = 'TRIGGERED',
    execution_id = :execution_id,
    updated_at = :now
WHERE occurrence_id = :occurrence_id
  AND claim_token = :claim_token
  AND status = 'CLAIMED'
  AND lease_until > :now
RETURNING *
```

**Atomic predicates verified:**
- `occurrence_id = :occurrence_id` — binds to exact occurrence
- `claim_token = :claim_token` — binds to exact current claimant
- `status = 'CLAIMED'` — only unhanded-off occurrences
- `lease_until > :now` — only valid lease owners

**No unsafe read-then-write race:** The handoff service reads job state first, then delegates to execution layer, then calls `finalize_triggered`. Between read and write, another claimant could potentially acquire the lease. But `finalize_triggered` re-verifies all predicates atomically in the UPDATE WHERE clause. A stale read cannot cause an invalid transition.

**Stale claimant rejection:** Any claimant without the exact `claim_token` or with expired lease fails the WHERE clause. `result.scalar_one_or_none()` returns `None`. Handoff service returns `HandoffResult(success=False)`.

**Expired lease rejection:** Handoff service checks `lease_until > now` at entry. `finalize_triggered` checks `lease_until > now` in WHERE clause. Both must pass.

### 19.2 Crash-Window Analysis

#### A. Crash before execution request
- **Scheduler state:** CLAIMED (valid lease)
- **Task/plan state:** Unchanged
- **Recovery:** Scheduler worker re-polls. Lease may expire → recovery resets to PENDING → re-claim → handoff.
- **Duplicate execution:** None

#### B. Crash while submitting execution
- **Scheduler state:** CLAIMED (transaction not committed or committed)
- **Task/plan state:** Unchanged
- **Recovery:** On restart, lease likely expired → recovery resets to PENDING → re-claim → handoff.
- **Duplicate execution:** None

#### C. Execution request accepted but process crashes before scheduler persistence
- **Scheduler state:** CLAIMED (TRIGGERED not recorded)
- **Task state:** RUNNING (with `execution_token` from atomic `claim_task_attempt`)
- **Plan state:** Background task running (in-memory `execution_id` only)
- **Recovery:**
  - **Task path:** RecoveryManager detects RUNNING task with stale heartbeat → existing recovery handles it. Scheduler recovery resets expired claim → re-claim → handoff → task CAS (`claim_task_attempt`) prevents duplicate claim because task is already RUNNING. **Duplicate task execution: IMPOSSIBLE.**
  - **Plan path:** Process restart loses in-memory `_plan_to_exec_id`. Scheduler recovery resets claim → re-claim → handoff → `BackgroundExecutionManager.start_execution()` sees empty `_plan_to_exec_id` → creates NEW background task. **Duplicate plan execution: POSSIBLE.** This is the documented unavoidable limitation.
- **Which component owns recovery:** 
  - Task: RecoveryManager (existing) + scheduler recovery
  - Plan: Scheduler recovery only; plan-level recovery not durably tracked
- **Can recovery distinguish "never handed off" from "accepted but scheduler crashed"?**
  - Task: Yes — task state is RUNNING with `execution_token`
  - Plan: No — in-memory execution state is lost on restart

#### D. Scheduler persistence succeeds but execution process crashes
- **Scheduler state:** TRIGGERED (with `execution_id`)
- **Task state:** RUNNING (with `execution_token`)
- **Plan state:** Background task crashed
- **Recovery:**
  - **Task:** RecoveryManager handles RUNNING task
  - **Plan:** BackgroundExecutionManager cleans up handle on next operation; tasks within plan may need individual recovery
- **Duplicate execution:** None

#### E. Execution starts but scheduler remains unaware
- **Scheduler state:** CLAIMED
- **Task state:** RUNNING
- **Recovery:** Same as case C. Task CAS prevents duplicate.
- **Duplicate execution:** Possible for plans, impossible for tasks.

#### F. Scheduler restarts with TRIGGERED occurrence
- **Scheduler state:** TRIGGERED (durable)
- **Task state:** RUNNING/VERIFYING/PASSED/COMMITTED/FAILED
- **Recovery:** 12.2E advances to next occurrence based on terminal task state.
- **Duplicate execution:** None

#### G. Stale claimant attempts handoff after lease expiry
- **Scheduler state:** CLAIMED (lease expired)
- **Recovery:** Another worker recovers via `reset_expired_claim_to_pending`
- **Stale claimant handoff:** FAILS — both handoff service pre-check (`lease_until <= now`) and `finalize_triggered` WHERE clause (`lease_until > :now`) block.
- **Duplicate execution:** None

### 19.3 Task Execution Identity Analysis

**`task.execution_token` properties:**
- **Durable:** Yes — persisted in `development_tasks.execution_token`
- **Unique enough:** Yes — `exec_{uuid.uuid4().hex[:12]}`, 96-bit collision resistance
- **Generated atomically:** Yes — generated and written in single `UPDATE ... WHERE status = :expected AND attempt_count < :max_attempts`
- **Not confused with occurrence_id:** Yes — `execution_token` is on `development_tasks`, `occurrence_id` is on `scheduled_jobs`
- **Not an authorization credential:** Yes — used only as execution reference, not for permission checks

**Scheduler retry cannot cause two simultaneous task executions:**
- `TaskRepository.claim_task_attempt()` is atomic CAS: `WHERE task_id = :id AND status = :expected AND attempt_count < :max`
- Only one concurrent worker can successfully claim
- If scheduler re-handoffs after crash, the task is already RUNNING, so `claim_task_attempt` fails
- `AutonomousRunController.start_run()` checks `task.status in (RUNNING, VERIFYING, PASSED)` and raises `TaskNotStartableError`
- Handoff service pre-check catches this before calling `start_run`

### 19.4 Plan Execution Identity Analysis

**`BackgroundExecutionManager.execution_id` properties:**
- **Durable:** NO — stored only in `_handles_by_exec_id` dict (in-memory)
- **Unique enough:** Yes — `exec_{uuid.uuid4().hex[:12]}`
- **Generated atomically:** Yes — generated before launching background task
- **Lost on restart:** YES — process crash destroys in-memory state

**Exact consequences:**
1. After process restart, `_plan_to_exec_id` is empty
2. Scheduler cannot distinguish "plan already executing" from "plan never started"
3. Duplicate plan execution is possible if scheduler re-handoffs after crash-before-TRIGGERED
4. Recovery must use plan-level durable markers (task execution_tokens, events) to reconcile
5. No durable plan execution identity exists in the current architecture

**This is a pre-existing architectural limitation, NOT a defect introduced by Stage 12.2D.**

| Stale claimant handoff | IMPOSSIBLE | IMPOSSIBLE | Token + lease checks |

### 19.6 Lease Race Analysis

**Concurrent handoff vs lease expiry:**

1. Handoff service checks `lease_until > now` at entry
2. If lease expires during `start_run` execution, handoff still completes
3. `finalize_triggered` re-checks `lease_until > now` atomically
4. If lease expired between entry and finalize, `finalize_triggered` returns `None`
5. Handoff service returns `HandoffResult(success=False)`

**Concurrent renew vs recovery:**
- `renew_lease` requires `lease_until > now`
- `reset_expired_claim_to_pending` requires `lease_until <= now`
- These are mutually exclusive atomic predicates

**Stale claimant after recovery:**
- Recovery clears `occurrence_id`, `claim_token`, sets `status = 'PENDING'`
- Stale claimant's `finalize_triggered` fails on `occurrence_id` (cleared) and `status` (PENDING ≠ CLAIMED)

### 19.7 Authorization Proof

1. Scheduler handoff → `AutonomousRunController.start_run(task_id)`
2. Controller fetches task, checks startability
3. Controller delegates to `AutonomousTaskOrchestrator.start_task()`
4. Orchestrator checks state machine transitions
5. Orchestrator calls `TaskStateMachine.claim_attempt()` — atomic CAS
6. Orchestrator runs verification, approval, commit via `VerificationGate`
7. Scheduler claim/lease is NEVER checked by any of these layers

**Plan path:**

3. Manager launches `AutonomousPlanExecutor.execute_plan()`
4. Executor delegates to `PlanExecutionService` → `AutonomousRunController.start_run()` per task
5. Same task-level authorization applies

**Scheduler claim/lease is NOT authorization.** It proves scheduler ownership of the occurrence only. If authorization/approval is unavailable, the execution layer rejects the handoff safely.
