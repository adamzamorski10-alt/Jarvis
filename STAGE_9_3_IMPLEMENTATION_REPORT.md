## 3. Final Architecture

```
UserIntent (application-controlled)
        |
        v
    AIManager
        |
        v
    ManagerResult / ManagerDecision
        |
        v
    ManagerPlanningService (APPLICATION BRIDGE)
        |
        +-- _check_eligibility(outcome)
        +-- _enforce_policy(decision)
        +-- _decision_to_user_plan(decision, project_id)
        |
        v
    UserPlan (application-controlled)
        |
        v
    PlanManager (existing public contract)
        |
        v
    ManagerPlanResult
        |
        v
    PlanService / TaskRepository (existing persistence)
```

MODEL PROPOSES. APPLICATION DECIDES. AUTHORIZED APPLICATION SERVICES EXECUTE.

The bridge is an APPLICATION component. It is not an AI provider. It is not an executor. It ends at planning/persistence.

## 4. ManagerDecision → Planning Mapping

The bridge NEVER blindly forwards the entire ManagerDecision. It explicitly maps only the fields that become planning input:

| ManagerDecision Field | Mapping | Control |
|-----------------------|---------|---------|
| `goal` | → `UserPlan.user_request` | Untrusted bounded text |
| `intent.user_request` | → `UserPlan.user_request` (via `goal`) | Untrusted bounded text |
| `intent.constraints` | NOT forwarded | Model cannot control planning constraints |
| `intent.context` | NOT forwarded | Model cannot control planning context |
| `proposed_actions` | NOT directly forwarded | PlanManager proposes its own tasks |
| `required_capabilities` | NOT directly forwarded | Planning authorization is application-controlled |
| `rationale` | NOT forwarded | Model cannot inject planning requirements |
| `warnings` | NOT forwarded | Model cannot inject planning requirements |
| `uncertainty` | NOT forwarded | Model cannot control planning confidence |

Application-controlled fields generated by the bridge:
- `plan_id`: deterministic SHA-256 hash of `intent_id:outcome:goal`
- `project_id`: from application parameter
- `acceptance_criteria`: empty (model cannot control)
- `planning_constraints`: application defaults
- `strict`: True (application default)

## 5. Application Policy Gate

Outcome eligibility:
- `READY_FOR_PLANNING` → eligible
- `PROPOSED` → eligible (only if no HIGH/CRITICAL risk actions)
- `NEEDS_CLARIFICATION` → blocked
- `NEEDS_APPROVAL` → blocked (no plan-level approval service exists)
- `REJECTED` → blocked

Additional policy enforcement:
- `PROPOSED` with HIGH/CRITICAL risk actions → blocked
- Execution-type capability namespaces (`tool_execution.`, `shell.`, `subprocess.`, `git.`, `workspace.`, `verification_gate.`, `permission_engine.`) → blocked

## 6. Approval Handling

The bridge does NOT invent an approval service. `NEEDS_APPROVAL` outcomes are blocked from planning. The existing `ApprovalService` is for tool call approval, not plan approval. Model-proposed `approval_required=False` is NOT treated as authorization.

## 7. Capability Handling

Model-proposed capabilities do NOT grant authorization. The bridge blocks execution-oriented capability namespaces from entering planning. If a capability registry existed, it would be checked here, but none exists yet.

## 8. PlanManager Boundary

The bridge calls `PlanManager.plan(user_plan)` through its public contract. It does NOT:
- access PlanManager internals
- write directly to task tables
- create task records itself
- calculate task IDs independently
- bypass plan fingerprinting
- bypass DAG validation
- bypass repository idempotency/concurrency

## 9. Idempotency Behavior

Repeated submission of the same ManagerDecision produces the same `plan_id` because it is deterministically generated from `intent_id:outcome:goal`. The existing `PlanManager` and `TaskRepository.create_tasks_idempotent()` remain authoritative for plan fingerprinting and duplicate detection.

## 10. Error Model

```python
ManagerPlanningError (base)
├── ManagerPlanningNotEligibleError — outcome not eligible for planning
└── ManagerPlanningPolicyError — decision violates application policy
```

Errors are bounded and do not leak:
- stack traces
- credentials
- API keys
- filesystem paths
- internal tokens
- SQL details
- provider secrets
